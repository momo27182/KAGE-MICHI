# 性能基準レポート

最終更新: 2026-08-09

## 目的

現行ハッカソン版の処理時間を区間別に計測し、最適化の優先順位と性能目標を決定する。

## 測定対象

- 基準実装: `archive/hackathon_2025/github_main_snapshot/app.py`
- ケース定義: `benchmarks/cases.json`
- 対象地域: 和歌山駅周辺、半径1.7km

## 計測区間

1. OSM道路取得
2. OSM建物取得
3. コンビニ・給水地点取得
4. 座標系変換
5. 影ポリゴン生成
6. 影ポリゴン結合
7. 全道路の日陰判定とコスト設定
8. 経路探索
9. GeoJSON・Folium地図生成
10. Streamlit初回表示全体

## 測定環境

- OS: Windows
- Python: 3.12.13
- 直接依存: ルートの`requirements.txt`で固定
- 全11依存のimport確認: 成功

## 初期目標

- 初回起動: 10秒以内
- キャッシュ後の起動: 3秒以内
- 地点変更後の経路再計算: 1秒以内
- 時刻変更後の表示: 2秒以内

実測後に、精度とのトレードオフを含めて見直す。

## ボトルネック

1. **実行時のOSM取得**：初回約225秒のうち、道路・建物・施設取得が約219秒を占める。製品では起動時取得を行わず、事前取得・加工済みファイルを配布または保存する。
2. **キャッシュ読込を含むデータ処理**：キャッシュ後でも3.22秒で、初期目標3秒をデータ処理だけで超える。OSMnxのレスポンス再解析ではなく、投影済み道路・建物をGeoParquet等で直接読む方式を検証する。
3. **影生成と結合**：キャッシュ後2.29秒。時刻変更目標2秒を影処理だけで超える。時間帯別の事前計算、地域タイル、空間絞り込みを検証する。

道路日陰判定0.13秒、経路探索0.002秒は、現範囲では主要ボトルネックではない。Folium生成・HTML化0.44秒は改善余地があるが、データ処理と影処理より優先度は低い。

## 次の判断

- Phase 2では、最初にOSMデータ取得をオフライン処理へ分離する。
- 投影済み道路・建物の保存形式を比較し、起動時3秒未満を目指す。
- 影は検索時に全建物から再生成せず、時間帯別またはタイル別の事前計算を検討する。
- 経路探索アルゴリズムの最適化は、現段階の優先課題にしない。

## Issue #4: 投影済みローカル成果物の読込

2026-08-10に、同じ和歌山駅周辺半径1.7kmのOSMnxキャッシュから投影済み成果物を生成し、ローカル読込を測定した。

| 項目 | 秒 |
|---|---:|
| キャッシュからの事前生成・保存 | 7.713 |
| 生成直後のローカル読込 | 1.152 |
| 連続読込1回目 | 1.055 |
| 連続読込2回目 | 0.846 |
| 連続読込3回目 | 0.944 |
| SHA-256検証追加後の再生成直後読込 | 0.757 |

対象は道路3,537ノード・10,262エッジ、建物7,870件、地点39件。従来のキャッシュ後データ取得・整形3.22秒に対し、投影済み成果物の読込は0.85〜1.15秒となり、キャッシュ後3秒目標内へ入った。検索時の外部取得は行わないため、初回約225秒のネットワーク待ちも実行時経路から除外できる。

この測定はWindows、Python 3.12.13、OSMnx 2.1.1で行った。生成時にOSMnx HTTPキャッシュを使用したため、manifestの取得処理日時より元のOSMレスポンスが古い可能性がある。
