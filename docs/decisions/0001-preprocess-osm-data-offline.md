# ADR 0001: OSMデータを検索時ではなく事前処理する

- 状態: 採用
- 決定日: 2026-08-09

## 背景

ハッカソン版は検索のたびにOSMから道路、建物、地点を取得している。基準ケースの初回実行は約225秒かかり、そのうちデータ取得・整形が219.62秒を占めた。HTTPキャッシュ後もデータ復元だけで3.22秒かかり、初回10秒・キャッシュ後3秒というP0目標を満たさない。

## 決定

- 対象地域のOSMデータは、利用者の検索処理とは別の前処理コマンドで取得する
- 道路、建物、地点を投影・整形した中間成果物として保存する
- Webアプリは中間成果物を読み込み、検索時に外部OSM APIへ依存しない
- 中間成果物には対象範囲、取得日時、入力条件、形式バージョンを記録する

## 理由

最大の待ち時間は経路探索ではなくネットワーク取得とGeoDataFrame生成である。HTTP応答だけをキャッシュしても復元処理が残るため、検索時に必要な形まで事前処理する方が性能目標と再現性の両方に有効である。

## 検討した代替案

- 検索のたびにOSMを取得する: 最新データを使えるが、初回待ち時間と外部API障害の影響が大きい
- OSMnxのHTTPキャッシュだけを使う: 実装は簡単だが、キャッシュ後でもデータ処理が性能目標を超える
- 経路探索アルゴリズムを先に高速化する: 単体約0.002秒のため効果が小さい

## 影響

- データ更新用のコマンド、保存形式、更新手順が必要になる
- 配布物の容量とデータライセンス表示を管理する必要がある
- 一方で、実行時間が安定し、オフライン検証と自動テストが容易になる
